## 1. Scenario 3 and 9 in detail (the financially decisive ones)

```
submit-approval                    200
decide-approval (accountant)       200
decide-approval (the creator)      403   ← segregation of duties
post  Idempotency-Key=k1           200
post  Idempotency-Key=k1 (replay)  200 → same journal_entry_id
post  Idempotency-Key=k2           409   ← second posting refused
post  (no key)                     400   ← key mandatory
POSTED entries in DB               1
POSTED entries balanced            1
trial balance                      11 900,00 / 11 900,00  balanced=true
```

The ordering matters: the refusal happens **before** any ledger write, and the count is
read from the table afterwards — not inferred from a response body.

## 3. Coverage gaps in the scenario set

- **No browser/desktop E2E.** Every scenario above is API-level or process-level; the
  GUI path is NOT EXECUTED (see `DESKTOP_ACCEPTANCE_REPORT.md`).
- **No multi-user, multi-company load scenario** — only two-thread concurrency.
- **No real supplier PDF** — all documents are synthetic, generated by the project's own
  renderer. A real, messy Algerian invoice is the most valuable missing input.
- **Scenario 8 is harness-level**, not a real public-CA staging deployment.

## 4. Verdict

All ten scenarios pass with **persisted-state assertions**. The gaps in §3 are the
honest boundary of that statement.
