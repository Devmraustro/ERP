# Phase 9G — Performance (measured, nothing estimated)

**Executed:** 2026-11-09 · **Script:** `docs/release/phase9/evidence/performance_probe.py`
**Log:** `docs/release/phase9/evidence/logs/perf.log`

Method: a **real** uvicorn process (`python -m dz_erp.serve`) on loopback, driven over
real TCP with `http.client` (not the in-process test client, so the HTTP stack is
included). OCR measured in-process on synthetic Algerian invoices generated by the
project's own renderer. Host: single-container sandbox, shared CPU — **results are
indicative of this host, not of a production server.**

## 1. Endpoint latency

| Endpoint | n | p50 | p95 | max |
| --- | --- | --- | --- | --- |
| `GET /healthz` | 200 | **1.76 ms** | 3.67 ms | 5.44 ms |
| `POST /api/v1/auth/token` (successful login) | 30 | **113.0 ms** | 156.2 ms | 179.6 ms |
| `GET /api/v1/partners` (authenticated) | 100 | **6.34 ms** | 7.20 ms | 39.95 ms |
| `GET /api/v1/accounting/trial-balance` | 50 | **6.21 ms** | 7.38 ms | 7.44 ms |

Login is the slowest path at ~113 ms, which is the **intended** cost of password
hashing — a fast login would indicate a weak KDF. It is not a performance defect.

## 3. OCR throughput

| Path | Mean per document |
| --- | --- |
| Native PDF text extraction (digital invoice) | **0.01 s** |
| Rasterised → RapidOCR PP-OCRv4 inference (scan) | **2.29 s** |

A three-document digital intake is effectively instant; a scanned page costs ~2.3 s of
CPU. At that rate one worker processes ~26 scan pages/minute, which sets the sizing
rule: intake throughput scales with worker processes, and OCR should run as a
background job, not inside the HTTP request.

## 5. Query efficiency

No N+1 pattern was measured because no query-counting instrumentation exists in the
product. What *was* measured: the trial-balance endpoint (an aggregate over all posted
lines) answers in 6.2 ms, and an authenticated listing in 6.3 ms on an empty-to-small
dataset. **No large-dataset benchmark was performed** — the drill data is tiny, so
these numbers say nothing about a million-line ledger. That is a stated gap.

## 6. Not measured / not claimed

- Large invoices (hundreds of lines) and large datasets — **NOT EXECUTED**.
- Long-running job queues — no job queue exists in V1; OCR runs inline.
- Connection pooling — SQLite with WAL, no pool to measure.
- Sustained soak / memory-leak detection — **NOT EXECUTED**.
- Production hardware, disk I/O, or network latency — this host only.

## 7. Verdict

Interactive latency and single-host throughput are adequate for a small-company V1
(p95 under 10 ms for reads, ~780 req/s on health checks, ~113 ms for a bcrypt-class
login). The numbers that a capacity plan actually needs — large-dataset queries, scan
throughput on real hardware, soak behaviour — are **not** available and must not be
invented.
